# Folveta 开发维护

本文说明网站 1.0 的运行与维护方式。功能范围见 [版本基线](版本基线.md)，搜索优化见 [SEO 优化](SEO优化.md)。实际配置以代码、锁文件和目标环境为准。

## 本地运行与常用命令

使用 Node.js 22+ 和 npm，按根目录 [README](../README.md) 安装依赖并配置 `.env.local`。不要覆盖已有配置，也不要提交真实密钥。项目使用 Next.js 16、React 19、TypeScript 和 Tailwind CSS 4。

| 命令 | 用途 |
| --- | --- |
| `npm ci` | 按锁文件安装依赖 |
| `npm run dev` | 本地开发，默认端口 3000 |
| `npm run check` | 依次执行 lint、类型检查、单元/契约测试、Workflow 测试与生产构建 |
| `npm run build` / `npm run start` | 构建 / 启动生产模式；先构建再启动 |
| `npm run test:browser` | 桌面和移动端 Chromium；默认自动启动 3100 端口服务 |
| `PLAYWRIGHT_BASE_URL=http://localhost:3000 npm run test:browser` | 使用已启动的指定服务，不另开服务 |
| `npm run fixtures:generate` | 重新生成合成 PDF/PPTX 测试夹具 |
| `npm run test:seo:responses` | 校验索引模式的生产构建，默认连接 3122 端口；启动方式见 SEO 文档 |

`/study/demo` 与 `/study/demo/quick-check` 可用于演示检查。普通测试使用合成数据；默认跳过的真实模型、数据库和自备材料测试需要显式配置，详见 `tests/live/`。测试通过不能代替真实账号、生成和支付验证。

完整浏览器回归按 [README](../README.md) 使用生产构建。默认开发模式可能额外执行身份读取，使支付模拟用例中“恰好两次请求”的断言失败；这是环境相关的测试限制，检查时同时核实最终用户身份与支付行为，不能只忽略失败。

`scripts/e2e/product-3b-e2e.mjs` 验证指南管理，`product-3c-e2e.mjs` 验证资料库、搜索与账户隔离；`package.json` 中对应 `setup / verify / cleanup` 命令会操作真实测试数据。只在已确认的隔离测试项目运行，结束后清理其夹具。`scripts/db/verify-generation-v2-persistence-db.ps1` 是本地 Docker/PostgreSQL 合约检查，包含写入与清理，需 PowerShell 和独立测试数据库。这些工具中的阶段名属于内部标识，继续保留以便维护。

## 配置入口

完整变量模板见 [.env.example](../.env.example)，服务端校验见 [lib/env.ts](../lib/env.ts)。模型名称与服务地址通过环境配置提供，不写死到业务代码。

| 分类 | 关键变量与要求 |
| --- | --- |
| 网站与索引 | `NEXT_PUBLIC_SITE_URL`、`PRELAUNCH`；Vercel Production 的域名必须为 `https://folveta.com`，公开索引使用 `PRELAUNCH=false` |
| 账户与存储 | `NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_ROLE_KEY`；默认私有桶 `course-materials` |
| 模型 | `OPENAI_BASE_URL`、`OPENAI_API_KEY`、各 `MODEL_*`；使用兼容 Responses 结构化输出的服务 |
| 生成与版本 | `AI_GENERATION_WORKFLOW_ENABLED`、`GENERATION_V2_RUNTIME_ENABLED`、`PROMPT_VERSION`、两项 `*_SCHEMA_VERSION`；保持与当前数据契约一致 |
| 后台任务 | `CRON_SECRET`、`RETENTION_JOB_SECRET`、`SESSION_RETENTION_DAYS`；任务密钥校验要求至少 32 个字符 |
| 支付 | `PADDLE_ENV`、`NEXT_PUBLIC_PADDLE_ENV`、客户端 token、API key、Webhook secret、产品与价格 ID；必须属于同一环境 |

只有明确用于浏览器的配置使用 `NEXT_PUBLIC_`。service role、模型密钥、Paddle API key、Webhook secret 和后台任务密钥只留在服务端。开发、Preview 与正式环境的数据库和凭据在操作前分别核对，不通过变量名推断是否隔离。

## 代码入口与数据流程

| 位置 | 维护职责 |
| --- | --- |
| `app/`、`components/` | 页面、API 与交互；视觉规范见 [DESIGN.md](../DESIGN.md) |
| `lib/server/parser.ts` | 格式检查、解析、来源单元与引用锚点 |
| `lib/ai/`、`app/workflows/` | 模型网关、生成契约、调度、恢复和持久化工作流 |
| `lib/server/generation-v2-persistence.ts` | 第二代生成引擎的数据库读写 |
| `lib/server/auth.ts`、`lib/server/supabase-auth.ts`、`proxy.ts` | 匿名/账户权限、登录与会话刷新 |
| `lib/server/guides.ts`、`library.ts`、`knowledge-search.ts` | 指南管理、材料库、私有全文搜索 |
| `lib/server/billing.ts`、`paddle.ts`、`paddle-webhook.ts` | 配额、订阅与支付事件 |
| `lib/site.ts`、`lib/seo.ts` | 规范域名、索引策略、共享元数据与结构化数据 |

主流程：浏览器创建会话 → 获取私有存储签名上传地址 → 服务端解析为来源单元/片段 → 生成请求通过权限、限流与配额检查 → 工作流调用模型并保存指南 → 页面读取结果 → 按需生成 Quick Check 并保存评分。

公共 HTML 可缓存，登录状态与限额通过 `/api/viewer` 获取，最近指南通过 `/api/guides` 获取；这些私有接口使用 `private, no-store`。不要为了显示登录信息把私有数据放进共享缓存。

数据库保留三类主要数据：

- 会话、来源、来源单元/片段、指南、Quick Check 与作答结果。
- 生成执行、操作、租约和 Workflow 实例；第二代引擎独立保存请求、分区产物、关联关系和最终指南。
- 按环境隔离的客户、订阅、额度、生成预留和 Webhook 事件。

具体表结构以 [有序迁移](../supabase/migrations/) 和 [数据库类型](../lib/server/database.types.ts) 为准。

## 生成引擎与恢复

网站版本 1.0 包含代码里已有的 Generation V1/V2 支持。`GENERATION_V2_RUNTIME_ENABLED` 控制新请求：关闭时走旧引擎，打开时走第二代引擎；旧版路径还受 `AI_GENERATION_WORKFLOW_ENABLED` 控制。已交付的两代指南保持可读。

持久化执行通过数据库状态、租约、幂等与重试授权避免重复结算；Workflow 实例编号本身不是数据访问或执行授权。第二代引擎支持分区产物复用和重试，部分缺口使用 `complete_with_gaps`；来源变化后旧请求不能生成混合来源结果。

切换引擎前，核对目标环境迁移、真实材料/模型生成、指南读取、Quick Check、配额结算和调度恢复。回滚新请求可关闭第二代引擎开关，同时保留已生成指南的读取。不要为了统一网站版本重命名引擎、删除兼容代码或改写数据版本。

## 数据库、权限与保留策略

数据库迁移是重建环境和同步数据库的必要材料，不能当作历史报告删除、压缩或重新编号。需要改表时追加迁移，使用项目已安装的 Supabase CLI：

```bash
npx supabase login
npx supabase link --project-ref <目标项目编号>
npx supabase migration list
npx supabase db push --dry-run
# 核对目标项目和变更后应用
npx supabase db push
npx supabase migration list
```

迁移不通过 service role 客户端或临时 Dashboard SQL 手工拼接执行。发现远程历史与本地不一致时，先查清差异再修复；不要直接重置数据库。本地链接状态位于被忽略的 `supabase/.temp/`。

匿名访问使用 `sgm_session`；登录后通过归属认领将当前匿名资料归到用户。账户数据采用所有者检查与 RLS，存储桶保持私有，不能用 `robots.txt` 代替鉴权。

- 匿名会话默认保留 7 天；登录资料不按匿名到期逻辑清理。
- 指南删除进入 30 天延迟清理；归档、恢复与删除是不同操作。
- 账户删除按私有对象 → 会话数据 → Auth 用户的顺序执行；Live 环境存在有效订阅时先阻止删除。不要只删除 Auth 用户留下关联数据。
- 过期清理先删 Storage，再删数据库；失败时需要检查剩余对象与关联数据。

生成恢复由 Supabase Cron 每分钟调用受保护的 `/api/internal/generation-reconcile`；迁移内包含调度配置。日常过期清理由 [vercel.json](../vercel.json) 每日 05:00 UTC 调用 `/api/internal/retention`。不要为同一恢复任务额外创建重复调度；本地文件存在不代表远程任务已正常运行。

## 支付维护

| 运行环境 | 服务端 `PADDLE_ENV` | 浏览器 `NEXT_PUBLIC_PADDLE_ENV` |
| --- | --- | --- |
| Sandbox | `sandbox` | `sandbox` |
| 正式收款 | `live` | `production` |

API key、客户端 token、产品、价格与通知目标均需匹配。支付入口使用服务端身份与配额检查，Webhook 位于 `/api/paddle/webhook`，处理前校验签名并去重；不能根据浏览器支付返回页直接授予 Pro。

数据库以 `billing_environment` 隔离客户、订阅、用量和事件。Sandbox 订阅不能赋予正式站权限。改价格或额度时同步公开页面、服务端配置、Paddle 和必要测试；以真实目标环境结果判断交易与退款状态。

## 发布、检查与回滚

1. 查看 `git status`，确认本次范围、版本和未提交内容，运行 `npm run check`。
2. 页面或素材有变化时运行浏览器测试；SEO 变化再运行 [SEO 响应检查](SEO优化.md)。涉及模型、支付和账户的变化追加对应隔离环境真实流程验证。
3. 准备发布时核对目标 Vercel 项目、生产分支 `main` 和变量；数据库变化先审阅迁移影响。Supabase Auth 的站点 URL、回调 URL 需与实际域名一致。
4. 发布后核对远程提交与对应部署成功状态，再检查首页、相关页面、图标、`robots.txt`、`sitemap.xml` 和受影响功能。
5. 服务异常先查看请求状态、数据库执行记录与 Vercel 日志；日志不记录原始课程材料、提示词或密钥。
6. 必要时回退到已知可用的应用部署；数据库不随应用回退盲目删表。生成开关按上节处理。只有确需暂停公开索引时才调整 `PRELAUNCH`，不要把取消索引当作通用故障修复。

当前操作是否已发布、迁移是否已应用、真实服务是否已验证，应在任务结果中说明；不为每次检查新增永久报告。旧验收细节通过 Git 查询。
